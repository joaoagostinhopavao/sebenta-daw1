Chapter 8

Databases and PHP

8.1 Relational Databases and the DBMS

A DBMS (Database Management System) is the software that creates, organises and manages databases: it controls access, queries and updates, guarantees the integrity, security and performance of the data, and allows applications, such as those written in PHP, to read and write information persistently. Common examples of DBMS include MySQL, MariaDB, PostgreSQL, Oracle, SQL Server and SQLite.

In a relational database, such as MySQL, data is organised into tables, each with fixed-type columns, and rows that represent individual records. It is exactly this persistence that the $artigos array seen in Section 3.8.3 lacks: the data lives in the PHP file, so publishing an article means editing the code, and nothing the program adds to the array is kept, because, on the next request (or on a refresh), the array goes back to holding only the articles written in the file. A database keeps information beyond each request, and shares it across all users, exactly what Tiago’s Contraponto site is missing to stop depending on data fixed in the code.

A database is organised on three levels: the MySQL server (the DBMS in operation) has several databases, and each database has several tables. In the Contraponto artigos table, each column is a kind of information (id, titulo, autor, categoria), each row is a record (a complete article), and the primary key (id) is a unique number that identifies each row.

8.2 SQL Commands

SQL (Structured Query Language) is the language used to interact with a relational DBMS. Its commands are divided into four main groups:

  • DQL (Data Query Language): queries that retrieve data, with the SELECT command;
  • DML (Data Manipulation Language): inserting, changing and removing data, with the INSERT, UPDATE and DELETE commands;
  • DDL (Data Definition Language): creating and altering database structures, with the CREATE, ALTER and DROP commands;
  • DCL (Data Control Language): permissions and access control, with the GRANT and REVOKE commands.

An SQL command follows a predictable structure: a keyword (SELECT, UPDATE, INSERT, DELETE), clauses that refine the statement (FROM, WHERE, ORDER BY, VALUES), expressions and conditions (fields, values and comparisons, such as age > 18), and a final semicolon:

SELECT titulo, autor FROM artigos WHERE id = 3;

An update command puts these same parts together in a slightly different way: command, then target table, the action of changing values, and a condition that filters which records are affected:

UPDATE artigos SET categoria = 'Tecnologia' WHERE categoria = 'Informática';

8.3 The Three-Tier Architecture and PHP’s Role

Returning to Section 2.1.3, a web application is typically organised into three distinct tiers: the client (browser), which displays pages and sends requests; the server, which processes the application’s logic; and the DBMS, which stores and manages the data. Separating these tiers increases the application’s security, performance and organisation.

It is worth following, step by step, how information flows through this model, with a concrete example:

  1. The client sends a request, for example GET /artigos.php?categoria=Cultura;
  2. The server (PHP) interprets the request and generates the corresponding SQL statement: SELECT * FROM artigos WHERE categoria = 'Cultura';
  3. The DBMS (MySQL) executes that statement and returns the results to the server;
  4. The server inserts that data into an HTML template;
  5. The server returns the final page to the browser, already filled with the requested data.

Each tier thus fulfils its own mission: the browser asks, the server thinks, the DBMS stores and answers, the server assembles the page, and the browser shows the final result to the user. PHP lives entirely on the server tier, responsible for receiving the client’s requests, building the SQL statements, communicating with the DBMS, processing the returned results, and generating the final HTML sent to the browser: it is the bridge between the user’s request and the data stored in the database.

8.4 Connecting PHP to MySQL

PHP connects to a MySQL database through the mysqli extension (MySQL Improved), a set of features added to PHP that allows it to connect to the MySQL server, send it SQL commands and receive the results, including prepared statements and transactions. It can be used in two styles: object-oriented or procedural. In this chapter the object-oriented style is used, the most common in real projects: an object is created with new, just like the DateTime seen in Section 5.2, and its functions (methods) are called with ->.

new mysqli() creates the connection object, which is stored in $conexao, and every request to MySQL goes through it. It takes four arguments, in order: the server where MySQL runs ("localhost"), the MySQL user PHP identifies itself with, that user’s password, and the database to use:

<?php
$conexao = new mysqli(
    "localhost",
    "utilizador",
    "password",
    "contraponto"
);

if ($conexao->connect_error) {
    die("Ligação falhou: " . $conexao->connect_error);
}

The connect_error property holds the error message if the connection fails, and die() prints that message and stops the program. Since PHP 8.1, mysqli also stops the program by itself when the connection fails; this check is the classic form and still works.

The procedural style does the same with a function instead of an object: mysqli_connect("localhost", "utilizador", "password", "contraponto") creates the connection and returns false if it fails, and mysqli_connect_error() returns the error message.

8.5 Creating Databases and Tables

Creating the database and creating the tables are two separate steps: first the “container” is created (the database), only then the internal structures (the tables). Like any other SQL statement, both can be done from PHP, through the query() method, which sends the SQL command to MySQL and returns success or failure:

<?php
$conexao->query("CREATE DATABASE IF NOT EXISTS contraponto");
$conexao->select_db("contraponto");

$conexao->query("
    CREATE TABLE IF NOT EXISTS artigos (
        id INT AUTO_INCREMENT PRIMARY KEY,
        titulo VARCHAR(150) NOT NULL,
        autor VARCHAR(100) NOT NULL,
        categoria VARCHAR(50) NOT NULL,
        resumo TEXT,
        data_publicacao DATETIME DEFAULT CURRENT_TIMESTAMP
    )
");

IF NOT EXISTS avoids an error if the database or the table already exists, and the select_db() method chooses the database to work with next.

Each column has a type, which defines what it can hold: INT (whole number), VARCHAR(150) (text of up to 150 characters), TEXT (long text) and DATETIME (date and time). Some columns also have a rule, and it is worth understanding the meaning of each one:

  • PRIMARY KEY (PK): unambiguously identifies each record in the table; no well-designed relational table should exist without one;
  • AUTO_INCREMENT: makes this field’s value increase automatically by one for each new record inserted, without the programmer having to calculate it;
  • NOT NULL: forces this field to always have a value, preventing it from being left empty;
  • DEFAULT CURRENT_TIMESTAMP: if no explicit value is given for this field when inserting a record, MySQL automatically fills in the current date and time.

In practice, creating the database and tables from PHP is an initial, rare step in a real application: the database structure of an application already in production is typically created and altered once, through dedicated administration tools, not on every script execution.

8.6 Fundamental Operations: CRUD in SQL

The four fundamental operations on stored data, CRUD (Create, Read, Update, Delete), correspond directly to four SQL commands.

Insert a new record (Create), with INSERT:

<?php
$conexao->query(
    "INSERT INTO artigos (titulo, autor, categoria)
     VALUES ('Roteiro cultural de outubro', 'Marco Antunes', 'Música')"
);

Read existing data (Read), with SELECT. The result’s num_rows property indicates how many rows were returned, and the fetch_assoc() method returns each row as an associative array, as seen in Section 3.8.3:

<?php
$resultado = $conexao->query("SELECT * FROM artigos");
echo $resultado->num_rows . " artigos encontrados";

while ($linha = $resultado->fetch_assoc()) {
    echo $linha["titulo"] . " - " . $linha["autor"] . "<br>";
}

Each call to fetch_assoc() returns the next row, and, when there are no more rows, it returns null and the while ends (Section 4.2.2). Each row’s associative array has one key per table column, including those the INSERT did not fill in: resumo comes back as null, and data_publicacao holds the date and time MySQL filled in by default. Each value is read through its key, as in $linha["titulo"].

This last construct, a while looping over the results row by row, is also the usual way to dynamically generate an HTML table from data returned by the database, turning each article into a <tr> row on the page — exactly what the $artigos array, seen in Section 3.8.3, did in memory.

Update (Update) and delete (Delete) existing records, with UPDATE and DELETE:

<?php
$conexao->query("UPDATE artigos SET categoria = 'Tecnologia' WHERE id = 3");
$conexao->query("DELETE FROM artigos WHERE id = 3");

Both UPDATE and DELETE always require a WHERE clause; forgetting it is one of the most serious and most common mistakes one can make with a database, because, without a condition filtering the affected records, the statement applies to every row in the table.

8.7 Prepared Statements

All the examples above, with fixed values written directly in the code, are useful for understanding the basic flow, but are not suitable for a real application. Building an SQL statement by directly concatenating values coming from the user, such as those from $_POST, has a fundamental problem: the text typed into the form becomes part of the command, and MySQL can no longer tell what is command and what is value, which causes errors and security problems (a topic covered in depth in Section 9.1):

<?php
$sql = "INSERT INTO artigos (titulo, autor, categoria)
        VALUES ('$titulo', '$autor', '$categoria')";

The correct alternative is to use prepared statements, which separate the fixed SQL statement from the values, which are only inserted afterwards: the statement is sent with question marks (?) in place of the values, and the values follow separately, so they are never read as part of the command. In PHP, a prepared statement has three steps: prepare() prepares the statement with the ? placeholders, bind_param() binds each variable to its ?, and execute() runs the statement with the real values. The advantages are protection against the problems mentioned, better performance when the same statement is executed multiple times, and cleaner code:

<?php
$titulo = $_POST["titulo"];
$autor = $_POST["autor"];
$categoria = $_POST["categoria"];

$stmt = $conexao->prepare(
    "INSERT INTO artigos (titulo, autor, categoria)
     VALUES (?, ?, ?)"
);
$stmt->bind_param("sss", $titulo, $autor, $categoria);  // "sss" = three strings
$stmt->execute();

bind_param() needs to know the type of each associated value, indicated by a letter:

  • s: string;
  • i: integer;
  • d: double (numbers with decimal places);
  • b: blob (binary data, such as images or files).

To query data with prepared statements, the pattern is that of INSERT, with one more step at the end: get_result() returns the result, which is traversed with the while, as in the previous example with query():

<?php
$id = $_GET["id"];

$stmt = $conexao->prepare("SELECT titulo, autor FROM artigos WHERE id = ?");
$stmt->bind_param("i", $id);  // "i" = one integer parameter
$stmt->execute();

$resultado = $stmt->get_result();
while ($linha = $resultado->fetch_assoc()) {
    echo $linha["titulo"] . " - " . $linha["autor"] . "<br>";
}

In this example, the id arriving through $_GET identifies a real article, read directly from the artigos table.

The same principle applies to UPDATE and DELETE: using prepared statements makes them safe, because the values are never interpreted as part of the SQL command itself.

8.8 Errors and Best Practices

Working with databases inevitably means dealing with errors. The most common fall into three categories:

  • Connection errors: incorrect credentials, the MySQL server being down, or the specified database not existing; the MySQL message is, for example, Access denied for user 'utilizador'@'localhost';
  • SQL errors: invalid syntax, wrong table or column names, missing quotes or commas in the statement; the message is, for example, You have an error in your SQL syntax;
  • PHP execution errors: using undefined variables, or calling fetch_assoc() on the result of a query that failed (in that case, the result is false, and PHP gives the message Call to a member function fetch_assoc() on bool). A simply empty result is not an error: fetch_assoc() returns null and the while ends.

During development, it is essential to enable the display of all PHP errors and warnings, something that should never remain active in a production environment, for security reasons: the error message reveals table and user names to whoever visits the site:

<?php
error_reporting(E_ALL);
ini_set("display_errors", 1);

mysqli always explains what went wrong, as long as the right information is read: connect_error shows problems with the connection itself, and error shows problems coming from MySQL regarding a specific query. Some general good practices, to always keep in mind when working with databases in PHP:

  • Use prepared statements whenever there is data coming from the user;
  • Show errors only during development, and hide them in production;
  • Clearly separate PHP, SQL and HTML code, each in its own place, so the code is easy to read.

8.9 A Complete CRUD Application

Putting together everything seen in this chapter, the natural next step for the Contraponto site is to give Rita, the editor, a way to manage articles without having to touch the database directly: a small article management application, on top of the artigos table created in Section 8.5, distinct from the public pages already sketched in previous chapters, and which is typically spread across several PHP files, each responsible for one operation:

  • config.php: establishes the database connection, and is included, with require, at the start of every other file, avoiding repeating the connection code in each one;
  • index.php: lists all existing articles (Read), and links to all the other operations;
  • add.php and insert.php: add.php presents an HTML form, with fields for the title, author and category, which sends its data by POST to insert.php, which, with a prepared statement, inserts the new article (Create) and redirects back to index.php;
  • edit.php and update.php: edit.php presents a form pre-filled with the data of an existing article, and update.php saves the changes (Update), for example after Rita corrects an error or changes an article’s category;
  • delete.php: removes an existing article (Delete).

The pattern repeats: one file shows the form, and the other receives the data and talks to the database.

config.php avoids repeating the connection: the code from Section 8.4 is written once in that file, and all the others start with require "config.php";, just like header.php and footer.php in Section 5.3. PHP replaces the require with the contents of the file, so in index.php the $conexao variable already exists, and, if the password changes, it is changed in a single place:

<?php
// config.php
$conexao = new mysqli("localhost", "utilizador", "password", "contraponto");

if ($conexao->connect_error) {
    die("Ligação falhou: " . $conexao->connect_error);
}
<?php
// index.php
require "config.php";

$resultado = $conexao->query("SELECT * FROM artigos");

Creating an article. add.php shows the form, which sends the data by POST (Section 7.5) to insert.php:

<form action="insert.php" method="post">
    <!-- titulo, autor and categoria fields, and the Guardar button -->
</form>

insert.php reads the data from $_POST, saves the article with the INSERT prepared statement seen earlier, and ends with a redirect:

<?php
require "config.php";

$titulo = $_POST["titulo"];
$autor = $_POST["autor"];
$categoria = $_POST["categoria"];

$stmt = $conexao->prepare(
    "INSERT INTO artigos (titulo, autor, categoria)
     VALUES (?, ?, ?)"
);
$stmt->bind_param("sss", $titulo, $autor, $categoria);
$stmt->execute();

header("Location: index.php");

The last line, header("Location: index.php"), adds a header to the response (Section 7.6): the response has status code 302, a redirect (Section 7.7), and the browser requests index.php, where the new article already appears. Without this line, Rita would be left looking at a blank page, because insert.php has no HTML.

Changing an article. In the index.php list, each article’s link carries the id in the URL itself, for example edit.php?id=3, just as already happened in artigos.php?id=5 (Section 7.4.4). edit.php reads that article, with a SELECT prepared statement, and shows the form already filled in. The id travels in a hidden field, which does not appear on screen but is sent along with the other data, so that update.php knows which article to change:

<form action="update.php" method="post">
    <input type="hidden" name="id" value="3">
    <!-- titulo, autor and categoria fields, already filled in -->
</form>
<?php
require "config.php";

$id = $_POST["id"];
$titulo = $_POST["titulo"];
$autor = $_POST["autor"];
$categoria = $_POST["categoria"];

$stmt = $conexao->prepare(
    "UPDATE artigos
     SET titulo = ?, autor = ?, categoria = ?
     WHERE id = ?"
);
$stmt->bind_param("sssi", $titulo, $autor, $categoria, $id);
$stmt->execute();

header("Location: index.php");

The "sssi" indicates three strings and one integer, in the order of the four ?.

Deleting an article. In index.php, the link to delete article 3 is:

<a href="delete.php?id=3">Apagar</a>

The browser requests that address with a GET, in which the id goes in the URL, with no form, and delete.php deletes only that article and returns to the list:

<?php
require "config.php";

$id = $_GET["id"];

$stmt = $conexao->prepare("DELETE FROM artigos WHERE id = ?");
$stmt->bind_param("i", $id);
$stmt->execute();

header("Location: index.php");

Anyone who types delete.php?id=3 into the browser deletes the article, which is why, as explained next, this management area would be protected by authentication.

The complete flow of the application can be summarised as follows: Rita navigates between simple, independent pages starting from index.php; each operation, add, edit or delete, communicates with the database through insert.php, update.php or directly in delete.php; and, once the change is saved, the application always redirects back to index.php, closing the cycle. In a real application, this management area would, of course, be protected by authentication, through sessions as seen in Section 7.9.2, so that only Rita, and not any reader, could use it.

This small project brings together what came before, forms, $_GET and $_POST (Section 7.5) and require (Section 5.3), with what was seen in this chapter: the mysqli connection, the CRUD operations and prepared statements, in an application organised into several simple pages, each with a single responsibility.

8.10 Challenge

With the connection to MySQL, the tables and the prepared statements, Contraponto finally stops depending on simulated data, as already announced in the previous chapter’s challenge. Starting from the starter file in Section 7.10, the challenge is:

  1. Create the contraponto database and the artigos table, with the structure defined in Section 8.5;
  2. Loop, with a foreach, over the $artigos catalogue used in memory since Section 3.9, inserting each of the five articles into the table, through a prepared statement;
  3. Rewrite the index.php listing to stop looping over the in-memory array, and instead query the artigos table directly, with a prepared statement that filters by the category chosen in $_GET["categoria"], just as it already did with the array in the previous challenge.

The starter file, with the database connection already set up, is available in Section C.6.
