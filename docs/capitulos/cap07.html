Capítulo 7

O Protocolo HTTP e Gestão de Estado

7.1 Os Componentes da Web

Tudo o que foi visto no capítulo anterior, camadas, encapsulamento, portas, endereços e DNS, é a infraestrutura sobre a qual assenta a própria Web. A Web, como sistema, assenta em três componentes fundamentais:

  • Uma linguagem de apresentação: o HTML;
  • Um esquema de endereçamento: o URI/URL;
  • Um protocolo de comunicação entre cliente e servidor: o HTTP.

Um URL (Uniform Resource Locator) identifica, de forma única, um recurso na Web, combinando o protocolo a usar (http, https), o nome do servidor (que o DNS traduz para um IP), a porta, e o caminho para o recurso pretendido dentro desse servidor. É precisamente o protocolo HTTP, construído sobre toda essa infraestrutura, que é o tema deste capítulo.

7.2 O Protocolo HTTP

HTTP (Hypertext Transfer Protocol) é o protocolo da camada de aplicação que permite que duas aplicações comuniquem entre si na Web. Na maior parte das vezes, uma dessas aplicações é um servidor web (como o Apache, o Tomcat ou o GlassFish) e a outra é um browser (como o Chrome, o Firefox ou o Edge). Funciona segundo um modelo de pedido-resposta: o cliente envia um pedido HTTP ao servidor, e o servidor devolve uma resposta HTTP. É este protocolo que o browser do leitor da Contraponto usa sempre que pede uma página ao servidor da revista.

7.3 O Que Acontece Quando se Escreve um URL

Vale a pena seguir, passo a passo, o que acontece entre o momento em que o leitor da Contraponto escreve contraponto.pt no browser e o momento em que a página inicial da revista aparece no ecrã, juntando tudo o que foi visto no capítulo anterior:

  1. O browser extrai o nome do servidor (hostname) do URL, incluindo o número de porta, se indicado, e consulta o DNS para obter o seu endereço IP;
  2. De seguida o browser abre um socket TCP, especificando o IP de destino e a porta a usar (por omissão a porta 80 para uma página web comum);
  3. Escreve uma mensagem de pedido HTTP e envia-a através desse socket TCP; se não for indicado explicitamente o nome de uma página web no URL, o servidor assume, por omissão, index.html (se esta não existir, procura outras páginas por omissão, como index.php, default.html, etc.);
  4. A camada TCP aceita a mensagem e garante a sua entrega fiável ao servidor, tal como descrito na Secção 6.3.1;
  5. O servidor responde, enviando uma mensagem de resposta que percorre o caminho inverso, através da mesma pilha de protocolos, até chegar de volta ao browser, que a interpreta e apresenta a página ao utilizador.

7.4 A Mensagem de Pedido

Uma mensagem de pedido HTTP completa tem a seguinte estrutura geral:

[método] [URL] [versão do http em uso]
[cabeçalhos]

[corpo]

O método indica a intenção do cliente. Os mais usados no desenvolvimento web são o GET e o POST.

7.4.1 O Método GET

O GET pede a obtenção de um recurso, sem que essa operação, por si só, altere nada no servidor: é o método usado sempre que se clica num link, como o que leva o leitor da Contraponto aos artigos de uma categoria:

<a href="contraponto.pt/artigos.php?categoria=Cultura">Cultura</a>

Pela mesma razão, o GET também pode ser usado num formulário, desde que o objetivo seja apenas obter um resultado, nunca alterar algo no servidor, como aconteceria se este mesmo filtro por categoria fosse feito através de um menu em vez de um link direto. É precisamente este pedido que a Secção 7.5 retoma, do lado do servidor.

Nota

A sintaxe exata de uma mensagem GET, incluindo o significado de cada uma das suas partes, está detalhada na Secção E.2.1.

7.4.2 O Método POST

O POST envia dados para o servidor, tipicamente para criar ou alterar um recurso: é o método usado, por exemplo, pelo formulário de comentário da Contraponto esboçado na Secção 3.2. Ao contrário do GET, os dados vão no corpo da mensagem, não na URL, e o pedido não é considerado inócuo: normalmente regista algo ou altera de alguma forma o estado do servidor. É também este pedido que a Secção 7.5 retoma, mostrando como o PHP recebe os dados que o leitor submeteu.

Nota

A estrutura completa de um formulário HTML e da mensagem POST correspondente está detalhada na Secção E.2.2.

7.4.3 GET vs. POST

A escolha entre GET e POST num formulário tem consequências práticas concretas:

  • Desvantagem do GET: os valores dos campos do formulário ficam visíveis na URL do browser. Por esta razão, o GET nunca deve ser usado se os dados do formulário forem sensíveis, como uma palavra-passe, e não devam ser partilhados ou ficar registados no histórico do browser;
  • Vantagem do GET: precisamente por os parâmetros ficarem na URL, esta pode ser marcada como favorita ou partilhada, permitindo voltar aos mesmos resultados sempre que necessário, tal como o próprio link de categoria da Contraponto visto na Secção 7.4.1; o POST não permite isto diretamente, porque os dados não ficam visíveis na URL.

7.4.4 Recursos Virtuais

Nem todos os recursos acessíveis através da Web existem, como tal, num ficheiro no servidor. Muitos são criados, ou montados “na hora”, de acordo com o pedido específico do cliente, depois de o servidor recuperar os dados necessários de uma base de dados, tema da secção Secção 8.1. Um pedido a artigos.php?id=5, por exemplo, não corresponde a um ficheiro chamado literalmente assim; corresponde à execução do script artigos.php, que, com base no parâmetro id, gera dinamicamente o conteúdo a devolver.

7.5 Supervariáveis

Falta uma peça para fechar o círculo: como é que o script artigos.php do exemplo anterior chega, de facto, ao valor 5 do parâmetro id? O PHP disponibiliza automaticamente, para isso, um conjunto de arrays predefinidos, conhecidos como supervariáveis (ou superglobais): variáveis automaticamente inicializadas pelo PHP, disponíveis em qualquer parte de um script, independentemente do contexto ou da função em que se esteja, sem necessidade de as declarar. É através delas que o código PHP tem acesso a tudo o que foi visto neste capítulo até aqui: os parâmetros de um pedido GET, os campos de um formulário POST, os cookies, a sessão. As mais usadas são:

  • $_GET: contém os dados enviados através da URL, exatamente o parâmetro id de artigos.php?id=5, ou os campos de um formulário submetido com method="GET", como visto na Secção 7.4.1;
  • $_POST: contém os dados enviados no corpo de um pedido POST, tipicamente por um formulário como o de comentário visto na Secção 7.4.2;
  • $_REQUEST: combina os dados de $_GET, $_POST e dos cookies do pedido, útil quando não interessa saber por que método os dados chegaram;
  • $_SESSION: guarda informação de sessão do utilizador, tema aprofundado mais adiante neste capítulo, na Secção 7.9.2;
  • $_COOKIE: contém os cookies enviados pelo cliente ao servidor, tema aprofundado na Secção 7.9.1;
  • $_SERVER: contém informação sobre o servidor e sobre o pedido atual, como o endereço do cliente, o método HTTP usado, ou o caminho do próprio script.

No sítio da Contraponto, $_GET é exatamente o mecanismo que permite a um leitor filtrar os artigos por categoria, através de um endereço como contraponto.pt/artigos.php?categoria=Cultura, substituindo finalmente, por dados reais de um pedido, a variável fixa usada na Secção 4.3:

<?php
// contraponto.pt/artigos.php?categoria=Cultura
if (isset($_GET["categoria"])) {
    echo "A mostrar artigos da categoria: " . $_GET["categoria"];
} else {
    echo "A mostrar todos os artigos.";
}

O uso de isset() no exemplo anterior não é acidental: aceder diretamente a uma chave de $_GET ou $_POST que não exista gera um aviso em PHP, pelo que é boa prática verificar sempre se um determinado campo foi de facto enviado antes de o usar, já que nem todos os leitores chegam ao sítio através de um endereço com esse parâmetro.

O $_POST, por sua vez, é o que recebe o formulário de comentário esboçado na Secção 3.2, quando um leitor o submete:

<?php
if ($_SERVER["REQUEST_METHOD"] === "POST") {
    $nome_comentario = $_POST["nome"];
    $texto_comentario = $_POST["texto"];
    echo "Comentário de $nome_comentario recebido: $texto_comentario";
}

As supervariáveis são o ponto de ligação entre o HTTP, do lado da rede, e a lógica em PHP, do lado do servidor: a filtragem por categoria e o formulário de comentário só produzem efeito porque os seus dados chegam ao script PHP através de $_GET ou $_POST. O código completo desta demonstração, incluindo o formulário HTML usado para testar $_GET e $_POST, está disponível na Secção B.3.

7.6 Cabeçalhos HTTP

Tanto o pedido como a resposta incluem cabeçalhos, pares de chave e valor com informação adicional sobre a mensagem, já presentes na estrutura genérica apresentada na Secção 7.4. O único cabeçalho obrigatório num pedido é o Host, que indica a que servidor o pedido se destina, essencial quando um mesmo endereço IP aloja vários domínios diferentes, como o próprio servidor da Contraponto.

Nota

Outros cabeçalhos comuns, como o Accept, estão descritos na Secção E.3.

7.7 A Resposta do Servidor

A resposta do servidor segue uma estrutura semelhante à do pedido, mas começa por uma linha de estado, em vez de um método e um URL:

[versão] [código de estado] [frase de razão]
[cabeçalhos]

[corpo]

O código de estado é um número que resume o resultado do pedido, agrupado em cinco categorias:

  • 1xx: informativo, usado raramente diretamente por quem programa aplicações web;
  • 2xx: sucesso, como 200 OK;
  • 3xx: redireccionamento, como 301 Moved Permanently, que indica que o recurso pedido passou a estar disponível noutro endereço;
  • 4xx: erro do lado do cliente, como 404 Not Found, quando o recurso pedido não existe, ou 403 Forbidden, quando o acesso é negado;
  • 5xx: erro do lado do servidor, como 500 Internal Server Error, que indica uma falha na aplicação do lado do servidor, tipicamente um erro no próprio código PHP.

7.8 HTTP é um Protocolo Stateless

O servidor HTTP não guarda, por si só, qualquer informação sobre o estado de ligações anteriores: depois de responder a um pedido, o servidor “esquece” essa ligação, uma propriedade chamada stateless (sem estado). Isto tem uma consequência prática relevante: uma única página web normalmente exige vários recursos, o próprio HTML, a folha de estilos CSS, o script JavaScript, eventuais imagens, e cada um destes recursos exige um pedido HTTP independente, cada um com o custo de estabelecer a sua própria ligação. Os browsers atenuam este custo com várias estratégias de gestão de ligações, mas o princípio mantém-se: cada pedido é, por si só, independente de todos os outros.

Se cada página tem mais do que um recurso e o servidor não guarda estado, como é que um sítio de comércio eletrónico sabe que artigos um utilizador colocou no seu carrinho, ou como é que a Contraponto reconhece um leitor que já comentou antes, sem lhe pedir de novo o nome em cada comentário? Para isso, o HTTP recorre a mecanismos de gestão de estado, como cookies e sessões, tema da secção Secção 7.9.

Nota

As estratégias concretas usadas pelos browsers para atenuar este custo, ligações paralelas, persistentes e em rajada, estão descritas na Secção E.4.

7.9 Gestão de Estado: Cookies e Sessões

Apesar de o HTTP ser, por natureza, stateless, o comportamento mais comum na Web é precisamente o oposto: um sítio de comércio eletrónico precisa de saber que artigos um utilizador colocou no seu carrinho, e a Contraponto, por exemplo, precisaria de reconhecer um leitor que já comentou antes, sem lhe pedir de novo o nome em cada comentário.

Antigamente, este seguimento de utilizador podia ser feito com base no endereço IP do cliente; com a popularização de redes onde vários dispositivos partilham um único IP público perante o resto da Internet (NAT, Network Address Translation), essa abordagem deixou de ser fiável, já que pedidos de utilizadores completamente diferentes podem chegar ao servidor com o mesmo endereço IP de origem.

Surgiram então duas soluções, complementares, para manter o estado de uma sessão entre pedidos sucessivos: cookies e sessões.

7.9.1 Cookies

Um cookie é um pequeno pedaço de informação que o servidor pede ao browser para guardar, inserido num cabeçalho da resposta HTTP, e que o browser passa a incluir automaticamente em todos os pedidos seguintes a esse mesmo servidor, permitindo a este reconhecer o cliente:

HTTP/1.1 200 OK
Set-Cookie: sessao=00b38b9a6f949a8df5476999c876789e; Path=/

Em PHP, um cookie cria-se com a função setcookie():

<?php
setcookie("utilizador", "joao", time() + 3600);

Um cookie, por si só, não constitui autenticação: apenas permite reconhecer que um pedido vem do mesmo browser que o recebeu anteriormente.

Nota

Os atributos que controlam a validade, o âmbito e a segurança de um cookie (Expires, Domain, Secure, HttpOnly, entre outros), bem como a norma que os define, estão detalhados na Secção E.5.

7.9.2 Sessões

As sessões vão mais longe do que os cookies simples: em vez de guardar os dados propriamente ditos no cliente, visíveis e alteráveis por quem tiver acesso ao browser, o servidor guarda os dados localmente, associados a um identificador único, e envia apenas esse identificador ao cliente, tipicamente através de um cookie. Em PHP, uma sessão inicia-se com session_start(), chamado no início de todas as páginas que a usem, e os seus dados ficam disponíveis através da supervariável $_SESSION:

<?php
session_start();
$_SESSION["utilizador"] = "joao";
<?php
// Noutra página, também com session_start() no início:
session_start();
echo "Bem-vindo, " . $_SESSION["utilizador"];

Cookies e sessões são, assim, a solução de engenharia que permite simular continuidade numa aplicação web construída sobre um protocolo que, por natureza, não guarda memória de nada entre um pedido e o seguinte.

7.10 Desafio

Com o HTTP e as supervariáveis, o sítio da Contraponto deixa finalmente de depender de dados simulados. O desafio, a partir do ficheiro de arranque da Secção 5.4, é:

  1. Substituir a variável fixa $categoria_escolhida, usada na Secção 4.3 para simular o filtro, pelo valor real de $_GET["categoria"], com isset() a tratar o caso de nenhuma categoria ser indicada;
  2. Confirmar, através dos links do menu em header.php (que já apontam para index.php?categoria=Cultura, index.php?categoria=Tecnologia, etc.), que a listagem de artigos muda de facto consoante a categoria escolhida no browser;
  3. Tratar a submissão do formulário de comentário, já incluído no ficheiro de arranque: verificar se $_SERVER["REQUEST_METHOD"] é "POST" e, nesse caso, ler $_POST["nome"] e $_POST["texto"], mostrando uma mensagem de confirmação ao leitor.

O ficheiro de arranque está disponível na Secção C.5.
